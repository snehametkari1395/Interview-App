# Prompt and model evaluation (LLM as a judge)

Results: [EVALUATION_RESULTS.md](EVALUATION_RESULTS.md) (generated by `scripts/run_evaluation.py`; also shown on the Evaluation page). See [MODEL_COMPARISON.md](MODEL_COMPARISON.md) for the current status of the open-weight run.

## What is evaluated

The output of chain B (interview question generation): a set of questions with topics, difficulty labels, expected answer points, follow-up questions, and hints, generated from a job description's context at a requested difficulty.

## Dataset (`evals/dataset.json`)

8 cases across 7 domains and all three difficulty levels:

| Case | Domain | Role | Difficulty |
| --- | --- | --- | --- |
| it-backend-medium | IT / Software Engineering | Backend Developer | Medium |
| ml-engineer-hard | AI / ML | Machine Learning Engineer | Hard |
| data-analyst-easy | Data Science | Data Analyst | Easy |
| finance-analyst-medium | Finance | Financial Analyst | Medium |
| hr-talent-medium | Human Resources | Talent Acquisition Specialist | Medium |
| product-manager-hard | Business / Management | Product Manager | Hard |
| pr-specialist-easy | Communication | Public Relations Specialist | Easy |
| platform-engineer-hard | IT / Software Engineering | DevOps / Platform Engineer | Hard |

Each case contains a realistic job description, a hand-written **job context** (the expected output of chain A: skills, competencies, interview topics), **expected topics** with keywords (the expected coverage of a good question set), and **quality notes** describing what a strong output looks like at that difficulty.

## Pipeline

For every configuration × case:

1. **Generate** with chain B, using the same job context, difficulty, focus, and count (3 questions) for every configuration.
2. **Deterministic checks** (`interview_app/evaluation/checks.py`, no LLM):

   | Check | Method |
   | --- | --- |
   | Schema validity | JSON Schema validation of the raw output |
   | Required fields | every question has text, a topic, ≥2 expected answer points, ≥1 follow-up |
   | Count | number of questions equals the request |
   | Difficulty label | fraction of questions labelled with the requested level |
   | Topic coverage | fraction of the case's expected topics whose keywords appear in the questions, topics, or answer points |
   | Repetition | maximum pairwise embedding similarity and number of duplicate pairs (MiniLM, the app's thresholds), mapped to 1–5 |
   | Follow-up distinctness | fraction of follow-ups that are not near-duplicates of their own question |
   | Readability | fraction of questions between 6 and 60 words |

3. **LLM judge** (`interview_app/evaluation/judge.py`): nine dimensions, each scored 1–5 with an explanation, plus weaknesses and suggested improvements.

   | Dimension | Anchors |
   | --- | --- |
   | Relevance to the job description | 5 every question targets a JD skill/topic · 3 role-relevant but generic · 1 unrelated |
   | Technical accuracy | 5 all expected answer points correct · 3 mostly correct, vague · 1 significant errors |
   | Question quality | 5 realistic, open-ended, discriminating · 3 generic or leading · 1 trivial or yes/no |
   | Difficulty alignment | Easy = one concept · Medium = applied situation · Hard = multi-constraint trade-offs; 5 all match · 1 wrong level |
   | Answer completeness | 5 expected points cover a strong answer · 3 misses important points · 1 superficial |
   | Clarity and readability | 5 concise and unambiguous · 1 confusing |
   | Repetition and semantic similarity | 5 distinct sub-topics · 3 overlap · 1 near-duplicates (higher is better) |
   | Follow-up question quality | 5 probes deeper into the same question · 3 generic · 1 irrelevant or restates |
   | Alignment with the interview domain | 5 authentic terminology and scenarios · 1 wrong domain |

   Scale: 1 very poor · 2 needs significant improvement · 3 acceptable · 4 good · 5 excellent.

4. **Report** (`interview_app/evaluation/report.py`): per-case scores with explanations, averages per dimension and overall, strongest and weakest dimension per configuration, deterministic results, model comparison (quality, latency, tokens, cost), prompt comparison, and recommendations.

## Comparisons

- **Models:** each open-weight model with the improved prompt (`v2-improved`) on the same cases.
- **Prompts:** on the primary model, `v1-original` (the app's original question-generation instructions) against `v2-improved`. The improved prompt adds grounding in job context, explicit difficulty definitions with example question shapes, a novelty rule that distinguishes duplicates from related sub-topics, requirements for checkable answer points and probing follow-ups, and a silent self-check. Both versions share the same output schema, so only the instructions differ.

## Reducing judge bias

| Bias | Mitigation |
| --- | --- |
| Self-preference (a model favours its own family's outputs) | The judge (Kimi K2) is a different family from all generators; the page warns if you pick a same-family judge |
| Position or order | Each output is judged twice, the second time with the questions in reverse order; per-dimension disagreement is reported |
| Verbosity | The rubric instructs the judge not to reward length or confident tone |
| Identity | The judge never sees which model or prompt produced the output |
| Randomness | Temperature 0, fixed rubric anchors, structured output |

**Noise threshold.** A difference between configurations is reported as meaningful only if it exceeds `max(0.3, 2 × mean judge disagreement)`. With 8 cases, smaller differences are not distinguishable from judge noise.

## Limitations

- A judge is itself a model: scores can vary between runs and judge models, and judges tend to favour fluent text despite instructions.
- Technical accuracy is judged without ground-truth answers, so a judge can miss subtle errors or penalise correct but unusual answers.
- Using a different family reduces but does not eliminate self-preference; using a single judge means the judge's own blind spots apply to every configuration.
- The dataset is small. It is suited to detecting clear regressions (for example a prompt that stops matching difficulty), not to ranking two close models.
- Deterministic checks are reliable but shallow: keyword coverage is a proxy for relevance, and embedding similarity a proxy for novelty.

## Running it

```powershell
uv run python scripts/run_evaluation.py                 # dry run: plan and cost estimate
uv run python scripts/run_evaluation.py --yes           # full run (default open-weight models)
uv run python scripts/run_evaluation.py --models qwen/qwen3-235b-a22b-2507,deepseek/deepseek-v3.2 --cases it-backend-medium,data-analyst-easy --yes
uv run python scripts/run_evaluation.py --judge none --yes   # deterministic checks only
```

The same run can be started from the Evaluation page, which also shows the dataset, results, and per-case judge explanations.
